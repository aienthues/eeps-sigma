Renamed JCEF Helper Execution

HighExperimentalWindows · process creation
Download .yml View on GitHub

What it detects

Detects execution of a binary whose PE OriginalFileName is jcef_helper.exe (the Java Chromium Embedded Framework helper) but whose on-disk name is different.

Why this rule exists

Kaspersky reports that the OxiDLLRunner loader used alongside the BlackX UEFI bootkit "is loaded by the legitimate file googleupdate.exe (original filename: jcef_helper.exe", and that the side-loaded DLL then "decrypts the contents of the file v8_context_snapshot.bin, which resides in the same folder".

Kaspersky attributes the intrusion to APT41 with medium confidence.

The attacker renamed a legitimate JCEF helper to googleupdate.exe to pass it off as an updater and use it as the side-loading host, so the rule keys on the name mismatch rather than on the googleupdate.exe name or the hash.

Assumption: the report's "original filename" is the PE version-resource OriginalFilename that Sysmon EID 1 and Defender record as OriginalFileName.

If the binary carries no version resource the rule will not fire.

detection:
    selection:
        OriginalFileName: 'jcef_helper.exe'
    filter_main_name:
        Image|endswith: '\jcef_helper.exe'
    condition: selection and not 1 of filter_main_*
falsepositives:
    - An application vendor that ships the JCEF helper under its own product-specific file name; check the signer and install path, and filter that path
level: high
Sysmon + Splunk Windows field mapping
source="WinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=1 OriginalFileName="jcef_helper.exe" NOT Image="*\\jcef_helper.exe"
Microsoft Defender XDR advanced hunting
DeviceProcessEvents
| where ProcessVersionInfoOriginalFileName =~ "jcef_helper.exe" and (not(FolderPath endswith "\\jcef_helper.exe"))
