Ivanti Connect Secure Welcome.cgi Request With X-DSCGI-PATH Header Pointing To Wu.cgi Or Runtime Tmp

HighExperimentalWeb server · webserver
Download .yml View on GitHub

What it detects

Detects requests to the unauthenticated Ivanti Connect Secure (ICS) sign-in script welcome.cgi (observed as /dana-na/auth/url_default/welcome.cgi)

Why this rule exists

that carry an X-DSCGI-PATH request header naming a different script: the protected upload handler /home/webserver/htdocs/dana/fb/smb/wu.cgi, or a file under /home/runtime/tmp/. Volexity reports that UTA0576 exploited CVE-2026-104935 this way: the URL path decides access, the X-DSCGI-PATH header decides which script runs ("This network request names a different script in its headers, X-DSCGI-PATH: /home/webserver/htdocs/dana/fb/smb/wu.cgi."). The actor then uploaded a Perl script with a .zip extension through wu.cgi, which was written to /home/runtime/tmp/<MD5(filename)>, and executed it by pointing X-DSCGI-PATH at that path. Commands and results travelled in these same HTTPS requests, rather than a separate command-and-control channel.

Logging prerequisite: native ICS access logs are not known to record request headers. This rule needs a TLS-terminating WAF, reverse proxy or decrypting NIDS in front of the appliance that logs the X-DSCGI-PATH request header. The field is named cs-x-dscgi-path following the W3C cs(<header>) convention used for cs-user-agent / cs-referer / cs-cookie; map it to your product's field (e.g. an nginx $http_x_dscgi_path log variable).
